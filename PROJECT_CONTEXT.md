# Adventurer's Kit — project context

Paste or attach this at the start of a new conversation. It describes what exists, how it fits together, and what is still open. Kept up to date as features land; see also `CLAUDE.md` (commands, architecture rules) and `Readme.md` (user-facing overview).

## What it is

A small self-hosted web app for running D&D 5e sessions. Everyone at the table opens it in a browser and sees the same live state.

**Rules baseline: D&D 2024** (SRD 5.2). The 2014 rules (SRD 5.1) are kept as the extra/legacy option: shared SRD names are plain for 2024 and "Name (2014)" for 2014, new characters and D&D Beyond imports default to 2024, edition pickers list 2024 first. Build new rules features for 2024 first; add 2014 behaviour where it differs and is cheap.

- **Home** (`index.html`): landing page with a card per tool (generated from the tool registry).
- **Combat Tracker** (`combat.html`): initiative order, HP, AC, conditions, death saves, rounds. PCs added from a sheet show its portrait (the client looks it up by `characterId` in `charState` rather than copying the image into combat state, which is broadcast on every HP click). Saved characters are added from here ("Add characters" panel, grouped by campaign with an "Add all" per campaign, with each player's initiative roll); every combatant's initiative is editable.
- **Concentration, condition icons and spell effects** (combat): combatants have `concentration` (spell name, '' = none), `concentrationDc` (CON save due after damage, 0 = none) and `effects: [{ id, name, casterId, concentration }]`. Actions: `setConcentration { id, spell, targets }` (ends the previous concentration and its effects, then adds a `concentration: true` effect to each target; players may only target combatants they can see), `endConcentration { id }`, `resolveConcentration { id, passed }` (failed → ends), `addEffect { id, name, casterId? }`, `removeEffect { id, effectId }`. Rules (`combat/service.js`): damage while concentrating sets `concentrationDc = min(30, max(10, ⌊damage/2⌋))` (temp HP doesn't avoid it); 0 HP, the conditions in `ENDS_CONCENTRATION` (Incapacitated, Paralyzed, Petrified, Stunned, Unconscious) and removing the caster end concentration, removing its effects from every target. Permissions: concentration actions → owner of the combatant; `addEffect` → owner of the target or of `casterId`; `removeEffect` → owner of the target or of the effect's caster. `playerView` blanks `casterId` when the caster is hidden. Client: icons in `public/js/core/effects.js` (🔮 concentration, one emoji per condition, spells by name with ✨ as fallback; `badgesFor(c)`); combat chips with icons, a purple "Concentrating: X" chip, a "CON save DC n" chip with Roll (PCs: d20 + CON mod + proficiency if `saveProf.con`) / Passed / Failed; "+ condition" also offers "Concentrating on…" and "Spell effect…". Casting from a combat row's Actions (`attacks.js` `renderActions` option `cast: { blocked, before, after }`): Cast is disabled under those conditions, a concentration spell while concentrating asks to confirm, and spells with concentration or a non-instantaneous duration open the target dialog (`public/js/core/spellDialog.js`, which builds its `<dialog id="spellDlg">` on first use; styles in `components.css`). The wiring of a combatant's Actions (slots, items, modifier toggles, cast hooks) lives in `public/js/core/combatActions.js`, shared by the Combat Tracker and the map card. Map/TV tokens show the icons as a column on the left edge (`map/render.js` `badgeRow`, 3 per cell of size, then "+n"), listed in the tooltip. Petrified was added to the condition list. Not modelled: War Caster advantage, spell durations/rounds, automatic modifier changes on targets (e.g. Bless's +1d4 is still switched on in their Actions).
- **Character Sheets** (`characters.html`): create, edit and store full character sheets with portraits, grouped into campaigns, import from D&D Beyond or a PDF.
- **Accounts and security** (2026-11-22; `src/features/accounts/` — service, route, index (wire `accountState`), links; `src/core/{identity,security}.js`; pages `login.html`, `join.html` (`js/login/`), `players.html` (`js/players/`, tool `players`, `dmOnly` + `accountsOnly`)). `KIT_AUTH` (config `AUTH_MODE`): **`accounts` (default)** or `open` (the trust-based mode below; the node tests use it via `test/helpers.js`, `test/accounts.test.js` sets `accounts`).
  - **Data**: `accounts.json` `[{ id, username, passHash (scrypt N=16384 r=8 p=1, per-password salt: "scrypt$N$r$p$salt$hash"), role: dm|player, characterIds, disabled, createdAt }]`, `invites.json` `[{ hash (SHA-256 of the code), role, characterIds, accountId ('' = new account, set = password reset), createdAt, expiresAt (7 days) }]`, `sessions.json` `[{ hash (SHA-256 of the token), accountId, createdAt, expiresAt (SESSION_DAYS, default 30) }]`. Excluded from backups and never touched by a restore (`backup/service.js` `AUTH_FILES`).
  - **Identity** (`core/identity.js`): `{ role, characterId, characterIds, accountId, username }`. Accounts mode: cookie `kit_session` (HttpOnly, SameSite=Lax, Secure when HTTPS or `COOKIE_SECURE=1`) → session → enabled account; role from the account (a DM may ask for less: `?role=player` — the TV); `characterId` = the requested one if it's the account's (a DM viewing as a player: any), else its first; `characterIds` is a live getter over the account (DM-as-player: + that one). `owns()` = DM or `characterIds.includes`. No session → `null`: the hub refuses the upgrade (401, `verifyClient`) and `/api/*` answers 401 (except `/api/auth/*`). Open mode: the old query/header identity (`characterIds = [characterId]`).
  - **REST** (`accounts/route.js`): public `GET /api/auth/status` (`{ mode, needsSetup, account }`), `POST /api/auth/setup {code, username, password}` (only while there is no enabled DM; the setup code is random per start and printed in the log, or `KIT_SETUP_CODE`), `POST /api/auth/login`, `POST /api/auth/logout`, `GET|POST /api/auth/invite/:code` (info / accept: new account with the invite's role + characters, or new password for a reset); logged in: `POST /api/auth/password {current, password}` (ends the account's other sessions); DM account only: `POST /api/accounts/invites {role, characterIds}` → `{code, path: '/join.html#invite=<code>', expiresAt}` (the code is only returned once), `DELETE /api/accounts/invites/:id` (id = first 12 hex of the hash), `PATCH /api/accounts/:id {role?, characterIds?, disabled?}`, `POST /api/accounts/:id/reset`, `POST /api/accounts/:id/logout`, `DELETE /api/accounts/:id`. The last enabled DM can't be demoted, disabled or deleted. Usernames 3–30 chars (letters, digits, space . _ -), case-insensitive unique; passwords 8–200.
  - **Live**: `accountState` = `{ mode, me }` (+ `list`, `invites` for a DM account in the DM view); rebroadcast after account REST calls, `addCharacter`/`deleteCharacter` and builder creates. `addCharacter` / `POST /api/builder/create` by a player account link the new character to it (`accounts/links.js`; an existing id is never linked), `deleteCharacter` unlinks it everywhere. Ended sessions (logout everywhere, password change, disable, delete) close the account's sockets with 4401; a role/disabled change also with 4403 (pages reload). Client `core/socket.js`: on 4401/4403/1006 checks `/api/auth/status` and goes to the login page if logged out; keeps `setAccount(accountState.me)`.
  - **Client identity** (`public/js/core/identity.js`): top-level `await fetch('/api/auth/status')`; accounts mode without a session → `/login.html?next=<page>` (the module never resolves, so page code doesn't run). `getIdentity()` validates the stored choice against the account (DM account: DM view unless it picked a character; player: one of theirs, or their only one automatically). `mayBeDm()`, `authMode()`, `currentAccount()`, `logout()`; `ownsCharacter` covers all of a player account's characters. "Who are you playing?" (join.js) shows *I'm the DM* only for DM accounts, `/api/characters/summary` returns only the player's own characters, and a footer "Signed in as … · Players (DM) · Change password · Log out". `login.html` (login / first-start setup → Players page), `join.html#invite=<code>` (the code stays in the fragment; reset links ask only for a password). Players page: invite form (role, characters), accounts (role toggle, disable, reset link, log out everywhere, delete; players' characters as chips with × and "+ Give a character…"), open invites (revoke).
  - **Hardening** (`core/security.js`, `app.js`, `hub.js`): `x-powered-by` off; security headers on every response (CSP `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline' fonts.googleapis.com; font-src fonts.gstatic.com; img-src 'self' data: blob:; connect-src 'self' ws(s)://<host>; frame-ancestors 'none'…`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, COOP, HSTS over HTTPS); non-GET `/api` and WebSocket upgrades must have a same-host `Origin`/`Referer` when they have one (403); failed-login limit 10 / 15 min per username and 30 per IP (`wait()` checks, only failures `hit()`, so a tunnel that hides client IPs doesn't lock a whole table out), setup/invite 30 / 15 min per IP, password change per account (`createRateLimiter`, in memory); WS `maxPayload` 4 MB; `TRUST_PROXY` (Express `trust proxy`) for `req.secure` / `req.ip` behind a proxy. Unknown usernames still cost one scrypt (no timing hint). Several tables per server: see "Admin, DMs and campaign tables" (libraries stay shared).

- **Admin, DMs and campaign tables** (2026-11-22, accounts mode; `src/core/{access,table}.js`). Account roles: `admin` (DM of every table, all accounts and campaigns, backups; the setup account; accounts from before roles: the oldest `dm` becomes `admin` on load; the last enabled admin can't be demoted/disabled/deleted), `dm` (may create campaigns), `player`. **Being DM is per campaign**: any account in a campaign's `dmIds` (any role, a player too) runs that table and plays its characters at the others — one login, DM in one campaign and player in another. Accounts gained `campaignIds` (campaigns it plays in, e.g. from an invite, without a character there yet); invites gained `campaignIds` (will play in), `dmCampaignIds` (will run — admin only; on accept the new account is added to those campaigns' `dmIds`; the Players page "Runs (DM of)" column) and `createdBy`; campaigns gained `dmIds` (creator on `addCampaign`; admin: `setCampaignDms {id, dmIds}`, any non-admin account).

The hub runs each action and builds each frame inside `withTable(identity.tableId)` (frame cache key includes the table), so combat/map code is unchanged otherwise.

Hub `dmPermissions` (new descriptor field): limits on a DM outside its table — characters: `updateCharacter`/`deleteCharacter`/`duplicateCharacter`/rests need `owns`; campaigns: `rename`/`delete`/`setActive` need `canDmCampaign`, `setCampaignDms` admin. `addCampaign` has a players' rule (a DM account with no campaign is at no table, so not `dm` yet).

- **DM / players** (`src/core/identity.js`, `public/js/core/{identity,join}.js`; in open mode identity is only this; with accounts see above): On first visit a "Who are you?" overlay (any page) offers *I'm the DM*, each character (from `GET /api/characters/summary` → `{ characters: [{id, name, class, level, portrait, campaignId}], campaigns: [{id, name}] }`; grouped under campaign headers — the active campaign first (★, and *Create a new character* goes into it), the others folded into "Other campaigns (n)" when there is an active one (opened if your character is only there), "No campaign" last, no headers without campaigns; each campaign heading has **+ New** to create a character in it (`addCharacter { id, campaignId }`), also for campaigns with no characters yet; the current character is marked "You"; when switching, Esc or a click outside closes it), or *Create a new character* (creates it as a guest, then opens `characters.html#create=<id>` — the sheet plus the guided creation). The choice is kept in localStorage (`kit.identity`) and sent as the WebSocket query (`?role=dm` / `?role=player&character=<id>`) and REST headers (`X-Kit-Role`, `X-Kit-Character`); no/unknown identity = player without a character. In open mode this is trust-based (anyone may pick DM); in accounts mode the server only grants what the account allows, and the query/headers merely pick among that.
  - **Hub**: each socket has an `identity`; frames are built per identity from an optional `snapshotFor(identity)`; actions are checked against an optional `permissions` map (`'anyone'` or `(payload, identity) => bool`). The DM may do everything; **an action with no entry is DM-only**.

  - **Players may** (`combat/permissions.js`, map/characters `index.js`): act on their own character only — its sheet (`updateCharacter`/`deleteCharacter`), combatant (HP, conditions, death saves, initiative, rename, remove, `addCharacterToCombat`), its familiar (`addFamiliarToCombat` and the familiar combatant), map token, and `nextTurn` when it's their turn; `addCharacter` is open to anyone. Everything else (monsters, campaigns, quick add, sorting, clearing, map size, `setCombatantDm {id, hidden?, alias?, dmNotes?}`) is DM-only. REST: new imports are DM-only (403), Sync is DM or owner.
  - **UI**: `body.is-dm` / `.is-player`; `.dm-only` / `.player-only` helper classes; nav badge to switch; other people's sheets are view-only; combat rows show 👁 hide/reveal and a "DM" section (alias for monsters, private notes) to the DM; `addMonsterToCombat` takes `hidden` ("Add hidden" checkbox).
- **Items** (`items.html`, feature `items`, wire `itemState`/`items`, saved to `items.json`): weapons (category, melee/ranged, `damage` dice + type, `versatileDamage`, `range` "normal/long", `properties`, `magicBonus`, `extraDamage` + type), armor (`armorType` light/medium/heavy/shield, `baseAc` — the bonus for shields, `maxDex` null = unlimited, `strengthReq`, `stealthDisadvantage`), gear (`effectDice` + `effect`, e.g. healing), plus cost/weight/notes. Dice are validated/normalised by `normaliseDice` (`NdX[+/-M]` with standard dice, or a flat number; invalid input keeps the old value). The library is seeded from the SRD (`src/srd/items.json`, see *SRD 5.1 + 5.2 content* below) when `items.json` doesn't exist, and new SRD versions are merged in once (a damaged file is left alone). `source` ('srd'/'custom') and `createdBy` ('dm' or a character id) are set by the server. Everyone receives the library; `addItem {id, patch}` needs a character (or DM); players update/delete only items they created; the DM anything. To-hit isn't stored on items — it depends on the wielder (ability mod + proficiency + `magicBonus`); used by character inventories and actions (below).
- **Inventory, Auto AC, actions** (character sheet *Equipment* and *Actions* tabs; combat rows): characters have `inventory: [{ id, itemId, name, qty, equipped }]` (library items; `name` is a fallback copy), `acAuto`, and `weaponProf: { simple, martial }` (D&D Beyond imports map `simple-weapons`/`martial-weapons`). Edited through `updateCharacter` like any sheet field, so the ownership rules apply. `characters/derived.js` `computeAc` (no armor 10+DEX; light +DEX; medium +DEX capped by `maxDex`; heavy no DEX; + shield; + `magicBonus`) — the characters slice and `addCharacterToCombat` use `withDerived`, and item edits rebroadcast characters. Characters saved before this, and imports, keep a manual AC (`acAuto: false`); new ones start on Auto; switching Auto off keeps the shown value. Client: `public/js/core/attacks.js` `buildActions` (equipped weapons: STR melee / DEX ranged / better of both for finesse; to hit = mod + proficiency if proficient with the category + magic; damage = dice + mod + magic, + extra damage, versatile alternative; gear with effect dice → Use; always an Unarmed Strike) and `renderActions` (Attack / Damage / 2-handed / Use buttons; a natural 20 arms a crit — doubled dice — for that action's next damage roll; Use spends one from the inventory). `public/js/core/dice.js` parses/rolls. Rolls are local to the roller's screen (not shared yet). Equipping body armor or a shield unequips the previous one. The old free-text `equipment` field stays as "Other equipment".
- **Actions list sections** (2026-11-18; `core/attacks.js` `renderActions`, so the sheet's Actions tab, combat rows and the map card): **Attacks** (equipped weapons, Unarmed Strike, Breath Weapon; header "Attack action: N attacks" from `features.js` `attacksPerAction` — Fighter 5/11/20, Barbarian/Monk/Paladin/Ranger 5), **Actions**, **Bonus Actions**, **Reactions**, **No action needed**, then **Spells** (spellcasting line on top; each spell tagged with its casting time — Action / Bonus Action / Reaction / "1 minute"…, `castingType`). Empty sections are hidden. Carried items with effect dice go to Actions, or Bonus Actions for potions under 2024 rules (`itemActionType`). Class and species features come from `public/js/core/features.js` `featureActions(ch)` (pure; catalog of ~30 2024 features with 2014 action-type overrides: Rage, Reckless Attack, Bardic Inspiration (die by level), Channel Divinity (cleric action / paladin bonus), Lay on Hands (pool), Wild Shape, Second Wind (rolls 1d10 + Fighter level), Action Surge, Indomitable, Martial Arts strike, Flurry / Patient Defense / Step of the Wind (Focus or Ki; the last two have a free version), Deflect Attacks, Hunter's Mark free casts, Cunning Action, Steady Aim, Uncanny Dodge, Innate Sorcery, Font of Magic (text only), Breath Weapon (DC 8 + CON + PB, 1–4d10 by level), Draconic Flight, Stonecunning, Large Form, Adrenaline Rush, Relentless Endurance, Luck). A feature shows when the class text has that class at that level, the race text has the species, or a sheet resource has its name (not for Channel Divinity, shared by two classes). Uses come from the matching resource ("2/3 left"); **Use** spends `cost` (`onSpendResource(id, n)` → `updateCharacter` resources; the sheet also redraws Resources), rolls when the feature has dice (through `rollBatch`, so "My dice" works), and for Rage also switches on the Rage modifier in the combat tracker. Lay on Hands asks how many points. Features with limited uses but no resource on the sheet suggest adding one. Not modelled: standard actions (Dash, Dodge…), subclass features, Eldritch Invocations, Metamagic options.
- **Roll my own dice** (top-bar toggle **✋ / 🎲** (icon only since 2026-11-22; "Hand dice" / "App dice" in its tooltip and aria-label), `core/nav.js`; per browser, `localStorage` `kit.manualDice`; **hand dice by default** since 2026-11-18 — only a stored `'0'` means the app rolls, so browsers that never touched the switch now ask for dice): every die goes through `core/dice.js` `rollDie(sides, label)`. Rolls that the player makes run inside `rollBatch(title, fn)`: automatic mode just runs `fn`; manual mode runs `fn` once with a recording source (missing dice return their max as a placeholder), asks for all of them in one dialog (`core/diceDialog.js`, registered via `setDiceAsker`; numbers 1–sides validated, "Roll the rest for me", Cancel/Esc → `RollCancelled` and nothing is spent), then replays `fn` with the answers. Great Weapon Fighting (2014) rerolls come from a separate `reroll` queue and are asked in a second round. A batch must not branch on its own dice otherwise — a spell attack and its damage are two batches (a crit doubles the damage dice). Covered: weapon Attack / Damage, item Use, Cast (attack, save, heal, auto damage) in `core/attacks.js` (`rolled()`; results shown on every copy of the action via `.action-result[data-key]`, since the list may redraw meanwhile), the concentration save Roll (combat), and spending Hit Dice on a short rest. Not covered: initiative (already typed into the Add-characters box, or rolled by the server when left empty) and the server-side monster initiative. On the map card, clicking inside it pins it so dialogs don't close it.
- **Monster actions** (DM only; `public/js/core/monsterActions.js`): `parseMonsterActions(notes)` (pure) reads the stat block from its first `— Actions —` heading on (sections Actions / Bonus actions / Reactions / Legendary actions; lines `Name: text`, continuation lines appended). Per entry: attack (`Melee/Ranged (Weapon|Spell) Attack: +N to hit` 2014, `… Attack Roll: +N` 2024), damage from the first sentence after `Hit:` (`X (dice) type damage`, flat `N type damage`; "plus"/"and" add, a comma or "or" starts an alternative labelled from the next words — Two-handed / Ranged / Melee / "With shillelagh"…; a "plus" after alternatives adds to all), saving-throw abilities (`DC N Ability saving throw` / `Ability Saving Throw: DC N`, damage from the failure sentence, `half` from "half as much damage" / "Success: Half damage"), and `(Recharge N–6)` in the name or text. On all 675 SRD creatures: 973 attacks (6 without damage — effect-only), 290 save abilities. `renderMonsterActions` shows each with its text and buttons: Attack (d20 + to hit, nat 20 arms a crit for that entry's next Damage), one Damage button per alternative, Recharge (d6) — all through `rollBatch`, so "roll my own dice" works. Wired through `core/combatActions.js` (`monsterFor` in the context; only when `isDm` and the monster has parsed actions): the Combat Tracker monster rows get an Actions section, the map card a pinned DM card. All state is shared live over a WebSocket. There are no accounts, no auth and no database.

## Architecture

Server is the single source of truth. Clients send action messages `{ type, payload }`; the server applies them and broadcasts the affected state slice to every client, including the sender (each client gets its own identity-filtered version). One slice per feature:

| Feature | Message |
|---|---|
| combat | `{ type: 'state', state }` |
| characters | `{ type: 'charState', characters }` |
| campaigns | `{ type: 'campaignState', campaigns }` |
| accounts | `{ type: 'accountState', accounts: { mode, me, list?, invites? } }` (per account) |
| monsters | `{ type: 'monsterState', monsters }` |
| items | `{ type: 'itemState', items }` |
| spells | `{ type: 'spellState', spells }` |
| map | `{ type: 'mapState', map }` |

On every new connection the server sends all of them. Each page ignores the message types it doesn't care about.

### Realtime hub and features

`src/realtime/hub.js` takes a list of **features**. A feature is `{ name, wire: { type, key }, snapshot(), snapshotFor?(identity), actions: { actionType(payload, identity) }, permissions?: { actionType: 'anyone' | (payload, identity) => bool }, alsoBroadcast?: { actionType: [featureNames] } }`. The hub builds an action → feature index (duplicate action names throw at startup), parses and validates incoming messages (non-JSON, non-object and unknown types are ignored), runs the action, then broadcasts that feature's slice plus any `alsoBroadcast` slices (an entry may be a function of the action's return value, e.g. `adjustHP`). Before running an action it checks `permissions` (DM may do anything; no entry = DM-only). REST routes can trigger a broadcast through `hub.broadcast(name)` (the importers via `onCharactersChanged` / `onItemsChanged` / `onSpellsChanged`, the map upload route via `onMapChanged`).

Layering inside a feature: `service.js` owns the state and plain operations; `actions.js` validates payloads and calls the service; `index.js` is the descriptor. Cross-feature dependencies: `combat/actions.js` → `characters/service.js` + `monsters/service.js` (adding them to combat), `combat/characterSync.js` → characters (sheet AC), `map/service.js` → `combat/service.js` (pruning tokens), `campaigns/actions.js` → `characters/service.js` (un-assigning on delete), and `characters/derived.js` → items + `public/js/core/modifier-presets.json` (AC).

### Combat state

```js
state = { round, activeIndex, combatants: [
  { id, name, init, ac, hp, maxHp, tempHp, type: 'pc'|'monster', conditions: [], deathSuccess, deathFail,
    characterId, monsterId,          // '' unless added from a sheet / the monster library
    size,                            // map footprint in cells (1–4), from the stat block for monsters
    hidden, alias, dmNotes }         // DM-only (stripped by playerView)
]}
```

Actions: `addCombatant`, `addCharacterToCombat { characterId, init? }` (PC from a saved sheet: AC, current/max HP; `init` is the roll result, omitted → server rolls d20 + DEX mod; ignored if that character is already in combat; combatant keeps `characterId`), `setInitiative { id, init }` (clamped −10..99, re-sorts keeping the active combatant), `removeCombatant`, `renameCombatant`, `adjustHP`, `addCondition`, `removeCondition`, `toggleDeathSave`, `setTempHp`, `nextTurn`, `sortInit`, `clearAll`, plus `addMonsterToCombat` and `setCombatantDm` (see Monsters / DM sections above). Combatant ids are generated server-side. Adding a combatant re-sorts by initiative while keeping the currently active combatant active (so `activeIndex` can shift on add).

### Character state

```js
{ id, portrait,               // portrait: base64 data URL ('' if none)
  name, race, class, level, background, alignment,
  ac, speed, hitDice,
  abilities: { str, dex, con, int, wis, cha },
  hpMax, hpCurrent, hpTemp,
  saveProf:  { str: bool, ... },
  skillProf: { 'Stealth': bool, ... },   // keys are the display skill names
  equipment,                  // newline-separated text ("Other equipment"); "Dagger x2" = quantity 2
  features,                   // newline-separated text, one entry per line
  notes,
  campaignIds, campaignId, ddbId,   // see Campaigns; '' = none
  inventory, acAuto, weaponProf,           // see Inventory, Auto AC, actions
  hitDiceUsed, pactMagic, resources, rulesEdition,   // see Short and long rests
  spellAbility, spellSlots, spells,        // see Spells
  modifiers }                              // see Attack modifiers
// Broadcast with derived fields from characters/derived.js (computed AC, acBreakdown).
```

Actions: `addCharacter { id }` (**id is generated by the client** so the editor can open immediately), `updateCharacter { id, patch }` (partial; `abilities`, `saveProf`, `skillProf` merged key by key; everything goes through `sanitizeCharacterPatch`: level 1–20, ability scores 1–30, name 60 chars, text fields 4000 chars, HP ≥ 0), `deleteCharacter { id }`, `duplicateCharacter { id, newId }` (DM only, 2026-11-20; sheet header **Duplicate**: a deep copy placed before the original, "Copy of …" (40 chars), `ddbId` cleared so a D&D Beyond sync can't overwrite it; portrait, inventory, resources, familiar and HP kept; the client picks `newId` and opens the copy). (Adding to combat is a combat action now, see above.)

Portrait validation: only `data:image/(jpeg|png|webp);base64,...` up to `MAX_PORTRAIT_CHARS` (derived from `config.MAX_PORTRAIT_BYTES` = 200 KB of image, ≈273k characters), or `''` to clear.

### REST import routes

- `POST /api/import/dndbeyond` — JSON `{ input }` (character URL or numeric id). Fetches `https://character-service.dndbeyond.com/character/v5/character/{id}` (unofficial; sharing must be **Public**), maps it, adds the character, broadcasts, responds `{ character }`. Errors respond `{ error }` (400 bad input, 502 non-OK from D&D Beyond, 404 unusable/private, 500 unexpected). Non-OK and unusable responses are now logged with status and the first 300 chars of the body.
- **Ability scores** (`mapper.js` `abilityModifiers` / `ddbStatValue`): `overrideStats` wins; otherwise base `stats` + `bonusStats` + every `type: 'bonus'` `<ability>-score` modifier from `modifiers.race`, `.class`, `.background` (2024 backgrounds' +2/+1), `.feat`, and `.item` only for items that are equipped (and attuned if `canAttune`; matched by `componentId` = `inventory[].definition.id`); `type: 'set'` modifiers (Gauntlets of Ogre Power…) raise the score to at least that value. **2024 rule**: when the background gives increases — `modifiers.background` score bonuses, or a feat named "<Background> Ability Score Improvements" (matched via `componentId` = the feat's definition id) — the `modifiers.race` score bonuses are skipped: D&D Beyond lists both (a 2024 species can carry an "Ability Score Increases" trait; legacy races keep fixed bonuses) but only applies the background's. Verified on a real 2024 Elf / Scribe character (2026-11-17). (Before 2026-11-17 only feat bonuses were counted.)
- **Avatars:** the mapper returns `avatarUrl` (`data.decorations.avatarUrl`, else `data.avatarUrl`); `client.fetchAvatar` fetches it only from `https://*.dndbeyond.com`, asks the CDN for 256×256 (`width/height/fit=crop/quality` query params — often ignored), then always resizes with `sharp` to a 256×256 JPEG (cover crop, q85, EXIF-rotated, transparency flattened to white). Any `image/*` sharp can decode is accepted; downloads over 15 MB are refused; the result must still fit `MAX_PORTRAIT_BYTES` (200 KB). Avatar tests are skipped when sharp can't load (Node < 20.9). Any failure just means no portrait (logged), never a failed import. Sync only fills the portrait if the character has none. If avatars never arrive, check the logs for "D&D Beyond avatar: skipped".
- `POST /api/import/dndbeyond/refresh` — JSON `{ characterId, input? }`. Re-imports into an existing character (the editor's "Sync from D&D Beyond" button, e.g. after leveling up). Uses the character's stored `ddbId` (saved on import); `input` links/re-links one. Replaces stats/proficiencies/equipment/features via `characters/service.refreshImported`, keeping portrait, notes, temp HP and damage taken (`hpMax - hpCurrent`). 404 unknown character, 400 no D&D Beyond id, otherwise same errors as above.
- `POST /api/import/pdf` — multipart field `file` (max 15 MB). Fillable form fields are matched against alias tables (case/punctuation-insensitive); unmatched non-empty fields go to Notes. Level is parsed from a combined `ClassLevel` field when there's no level field ("Fighter 3 / Wizard 2" sums to 5). No form fields → raw extracted text into Notes. Responds `{ character, warning }`.

Both importers create the character via `characters/service.addImported` using the same sanitizer as normal edits; the page then opens the new character's editor for review. Keep mappers pure (no network/files) so they stay testable.

## Frontend behavior worth knowing

- Shared pieces: `core/socket.js` (reconnecting WebSocket, handlers keyed by message type), `core/nav.js` renders the top nav from `core/tools.js` into `<nav class="app-nav" data-active="<id>">` — a `.nav-tabs` strip (🏠 icon only, then each tool's `short` name — Combat, Characters, Monsters, Items, Spells, Map; it scrolls sideways when it doesn't fit, with a thin scrollbar, vertical mouse wheel → horizontal, and faded edges via `more-left`/`more-right`; under 760 px inactive tabs show only their icon) and a fixed `.nav-side` with the dice switch and the identity badge (👑 DM / 🧝 name, truncated); the same registry builds the home cards (with the full `title`). To add a tool: add a registry entry, a page, `js/<id>/`, `css/pages/<id>.css`, and a server feature. Top bar on screens ≥ 900 px: `min(1280px, 100vw − 48px)` wide, centred over the page column (`position: relative; left: 50%; transform: translateX(-50%)` in `components.css`), so all tabs fit.
- **characters**: a player with a character lands on their own sheet's editor (once per page load, `openOwnSheet` in `characters/main.js`; "Back to list" still shows everyone); the DM and guests land on the list. List view (cards with avatar, name, race/class, level pill, AC/HP/speed, HP bar), import panel (D&D Beyond tab, PDF tab with drag-and-drop), editor view (hero panel, vitals tiles, HP panel, tabs Stats / Equipment / Actions / Spells / Features / Notes). Modifiers, saves, skill bonuses, proficiency bonus and initiative are computed client-side, never stored.
- Text edits are debounced 300 ms before sending; the server echoes full state to everyone.
- **Pending-edit tracking** (`characters/store.js`: `touch()` / `mergePending()`): fields touched in the last 2.5 s keep their local value when new state arrives; focused fields are never overwritten. This fixed a real race where an echo from an earlier edit overwrote newer typing. Keep it when changing the editor.
- Portraits are cropped to a centered square and resized to 256 px JPEG in the browser. They are part of the character object, so every `charState` broadcast carries all portraits — fine at table scale.

**Design system** — D&D Beyond-inspired: dark top nav with a red underline on the active page, red accent (`--wax`), amber secondary (`--gold`), Roboto Condensed uppercase headings, Roboto body (Google Fonts), light/dark following the OS (`prefers-color-scheme`, `data-theme` overrides). Tokens live in `css/tokens.css` (`--bg`, `--bg-panel`, `--ink`, `--ink-soft`, `--line`, `--wax`, `--gold`, `--good`, `--blue`, `--nav-bg`); `base.css` and `components.css` are shared; each page has its own `css/pages/*.css`. Pages link the three shared sheets plus their own.

## Known gaps and caveats

- The D&D Beyond endpoint is unofficial and can change without notice; the live import was tested by the user (2026-11-16). Non-OK responses are logged (`docker compose logs`).
- D&D Beyond **AC is a best-effort estimate** from equipped armor and shield; skill/save proficiencies come from scanning `modifiers` arrays and may miss sources. The import adds a note saying so.
- PDF alias table is heuristic; the official sheet's exact field names were not verified. Flattened/scanned PDFs only yield raw text.
- No authentication: DM/player roles are trust-based (anyone may pick DM); they only keep DM-only data off players' screens.
- **Browser tests** (2026-11-20): `npm run test:e2e` = Playwright (`@playwright/test` 1.60 — the last line that runs on Node 18 — dev dependency only; `npx playwright install chromium` once). `playwright.config.js` starts `node server.js` on port 3199 (`E2E_PORT`) with a temporary `DATA_DIR`, one worker. `e2e/helpers.js` (`as(page, 'dm' | characterId | null)` sets `kit.identity` before load, `watchErrors` — page errors and console errors, Google Fonts blocked — `send([[type, payload]…])` / `snapshot(wireType)` over WebSocket as the DM). `e2e/smoke.spec.js`: every page as DM and player, the first-visit join screen; `e2e/flows.spec.js`: Allies (current campaign first, others folded) + resource chips, Enemies (load SRD, search, add ×2, hidden quick add), map join → tray, campaign manager, duplicate, guided creation (Fighter/Dwarf/Soldier), level up, capped lists, off-hand / Nick attacks, retire + Show retired, creation at level 3 (Weapon Mastery picks, chained level-up dialogs). Specs are `*.spec.js` in `e2e/` so `node --test` doesn't pick them up. Selectors: combat rows by the badge label "Initiative for <name>" (names are input values, not attributes).
- Mobile: every page was checked at 360–390 px (headless Firefox screenshots, 2026-11-16). Combat rows have a phone layout (`@media (max-width: 600px)` in `combat.css`: Visible/Remove under the row, −5/−1/+1/+5 buttons ≥ 36 px, temp HP + bar on a second line). Other pages had no horizontal overflow; the nav, sheet tabs and battle map scroll sideways on purpose (map cells ≥ 32 px, tokens are `touch-action: none`). Items and Spells show the first 30 rows of each group with a "Show all N …" button (`core/cappedGroup.js` `createCappedGroups`, 2026-11-20; expanded groups stay open until a filter changes); Monsters caps at 120. The TV view is meant for landscape screens.
- Fonts come from Google Fonts at runtime; offline they fall back to system fonts.
- Client scripts are ES modules, so the pages need to be served over HTTP (not opened from disk).
