# Adventurer's Kit

A self-hosted D&D 5e toolkit for the table: a **Combat Tracker**, **Character Sheets** (with D&D Beyond and PDF import), a **Monsters** library, an **Items** library (SRD weapons/armor/gear + custom items), a **Spells** library (common SRD spells + custom ones; characters get spell slots and cast from their Actions) and a grid **Battle Map**, synced live across every device connected to the server. One player bumps a monster's HP and everyone's screen updates instantly.

A small Node server holds the state (saved to JSON files on disk, including the current fight) and pushes updates to every browser over WebSocket. No accounts, no database, no build step.

## Run it

### With Docker (recommended)

```bash
docker compose up -d --build
```

Open **http://localhost:3000**. Stop with `docker compose down`, follow logs with `docker compose logs -f combat-tracker`. Data lives in `./data`.

`docker-compose.yaml` is set up to be put online with Tailscale Funnel or another HTTPS tunnel/proxy on the same machine (see [Putting it on the internet](#putting-it-on-the-internet)): it listens only on this machine (`127.0.0.1:3000`), trusts the proxy and sends the login cookie over HTTPS only. To use it on your home wifi without a tunnel instead, change the port line to `"3000:3000"` and remove `COOKIE_SECURE` (both are marked "home wifi" in the file). It also has a health check (`docker compose ps` shows *healthy*) and rotates its logs.

The image bakes the code in, so **any change needs a rebuild** (`docker compose up -d --build`). For testing changes, the dev file mounts your folder and restarts on every change:

```bash
docker compose -f docker-compose.dev.yml up --build     # http://localhost:3001
```

It runs **next to** the real one without touching it: its own project (`dnd-kit-dev`), port **3001** and data folder **`./data-dev`** (git-ignored). On a fresh `data-dev` the admin setup code is `DEV-SETUP`; uncomment `KIT_AUTH: open` in it to skip logins for quick UI checks.

### Without Docker

```bash
npm ci
npm start
```

Requires Node 20.9+ (for `sharp`, which resizes imported avatars; on older Node the app still runs but D&D Beyond avatars are skipped).

### Tests

```bash
npm test
```

Runs the server tests (`node:test`, no extra dependencies): WebSocket flows for both features, input sanitising, and the importers' mapping logic.

```bash
npx playwright install chromium   # once: downloads a headless Chromium (~110 MB)
npm run test:e2e
```

Browser smoke tests (Playwright, a dev dependency — not installed in the Docker image): every page opens without script errors as the DM and as a player, plus the main flows (join screen, Allies/Enemies panels, resource chips, campaign manager, duplicate, guided creation, level up, capped library lists). They start their own server on port 3199 with a temporary data folder, so your `data/` is never touched.

## Letting friends connect

- **Same wifi**: they open `http://<your-LAN-IP>:3000`. Find your IP with `ipconfig getifaddr en0` (Mac) or `ipconfig` (Windows).
- **Different networks**: see [Putting it on the internet](#putting-it-on-the-internet) (HTTPS via a tunnel or a reverse proxy). Everyone logs in — see [Accounts](#accounts-dm-and-players).

## On phones

On a narrow screen the pages move to a bar at the bottom, and players get their turn and HP pinned above it on the Combat page. Players can also **install the kit as an app**. On Android (Chrome), use the menu → *Install app* / *Add to Home screen*. On iPhone (Safari), use Share → *Add to Home Screen*. It then opens full screen with its own icon. An installed app on iPhone keeps its own login, separate from Safari, so you log in once more there. The icon is `public/icons/icon.svg`. After changing it, run `node scripts/build-icons.js` to redraw the PNGs (uses Playwright's Chromium).

## SRD content

The item, spell and monster libraries come with the full **System Reference Document 5.1 (2014 rules) and 5.2 (2024 rules)**: every SRD spell, weapon, armor, piece of gear, magic item and creature. The table plays **2024 rules**: where both editions have the same entry, the 2024 one has the plain name and the 2014 one is "… (2014)" (libraries saved with the older naming are renamed automatically, keeping each entry's id). This is the openly licensed (CC-BY-4.0) part of D&D — content that's only in the paid books (the rest of the Player's Handbook, Xanathar's, …) isn't included; add it as custom entries. See [NOTICE.md](NOTICE.md).

The data lives in `src/srd/*.json`, generated by `scripts/build-srd.js` from the open [5e-bits/5e-database](https://github.com/5e-bits/5e-database). To regenerate it, download `src/2014/en/5e-SRD-{Spells,Equipment,Magic-Items,Monsters}.json` and the same four from `src/2024/en/` into a folder as `2014-Spells.json`, …, `2024-Monsters.json`, then run `npm run build:srd -- <folder>`. On the next start, each library merges the new data in once (SRD entries are updated in place, custom ones are left alone).

## Creating characters and leveling up

**+ New character** on the Character Sheets page (and *Create a new character* on the "Who are you?" screen) opens a step-by-step creator for the **2024 rules**: class → species → background → ability scores (standard array, point buy, 4d6 drop lowest — your own dice when the top bar shows ✋ (hand dice) — or your own numbers) → skills (plus Fighting Style / Expertise where the class gets them) → spells (and a Warlock's Eldritch Invocation) → starting equipment (and Weapon Mastery weapons) → name and **starting level**. Above level 1, the level up opens right after, once per level ("level 2 of 5"…), with the average HP already chosen; closing it keeps the levels done so far. It fills in the whole sheet: HP, saves, skills, feats, attack modifiers, spell slots, class resources, gear and gold, and the rules text of every trait and feature in Features. **Blank sheet** still gives an empty sheet to fill in by hand.

**⬆ Level up** on a sheet adds one level: pick the class (or multiclass into a new one, if you have the 13s), take the average or roll for hit points, and answer what that level asks for — subclass, Ability Score Improvement or a feat, Epic Boon, Fighting Style, Expertise, new cantrips and spells, Weapon Mastery weapons (set on the Weapon Mastery attack modifier's "only for"), Eldritch Invocations and Metamagic options (the Content page's, which also put their action or attack modifier on the sheet — Agonizing Blast, say — or any name typed in). Leaving a pick empty adds a "To do" note instead. Hit Dice, spell slots (multiclass table and Pact Magic included), class resources (Rage, Channel Divinity, Focus Points…) and the new feature texts are updated for you. It also works on characters imported from D&D Beyond or typed in by hand (it reads the class from the sheet, e.g. "Fighter 3 / Wizard 2"); classes that aren't in the SRD are kept but leveled by hand.

**Two-weapon fighting:** with two Light weapons equipped (or a pair of one, quantity 2) the Actions list adds each one's **off-hand** attack under Bonus Actions — without the ability modifier on its damage, unless the character has the Two-Weapon Fighting style (a modifier; the builder adds it with the feat). Under 2024 rules a weapon with the **Nick** mastery (and Weapon Mastery on it) makes it part of the Attack action instead; 2014 sheets use melee Light weapons only.

The rules come from the SRD 5.2, so each class has one subclass, and there are four backgrounds and only the SRD feats. For anything from the books, choose "Other" (subclass, feat) and add its text to the sheet, or add it on the Content page. Languages are listed as a "by hand" reminder. The data is `src/srd/rules-2024.json`, generated by `scripts/build-rules.js`: download `src/2024/en/5e-SRD-{Classes,Levels,Features,Subclasses,Species,Subspecies,Traits,Backgrounds,Feats}.json` from 5e-database into a folder as `2024-Classes.json`, … and run `npm run build:rules -- <folder>`.

## Custom content (subclasses, species, backgrounds, feats, class options)

The guided creation ships with the free rules (SRD 5.2): all 12 classes but one subclass each, 9 species, 4 backgrounds and the SRD feats. On the **📚 Content** page DMs and the admin add more — from their own books (e.g. the Player's Handbook) or homebrew — each with a **source tag** ("Player's Handbook (2024)", "Homebrew"…):

- **Subclass:** its class, a summary, and its features with the class level each arrives at (level up adds them to the sheet at those levels). Optionally:
  - **Resources** it gives (e.g. Superiority Dice: `3:4, 7:5, 15:6` = 4 at level 3, 5 at 7, 6 at 15 — or `PB` for the proficiency bonus, or an ability such as `CHA` for its modifier, at least 1), refreshed on a short or long rest: level up adds them to the sheet's Resources.
  - For each feature, **Used as** (Action / Bonus Action / Reaction / no action) and the resource it **spends**: it then appears in the sheet's Actions list, with a **Use** button that spends it.
  - **Always prepared** spells on a feature (domain / patron / oath spells): one line per class level, e.g. `3: Detect Thoughts, Dissonant Whispers` and `5: Clairvoyance` — or paste the rows of the book's table. Level up puts each spell in the spellbook at its level, marked *always prepared* (it doesn't count against the spells you prepare); names are matched to the spell library (apostrophes don't matter, and "Tasha's Hideous Laughter" finds the SRD's "Hideous Laughter"), and any that aren't in the library are listed on the sheet to add by hand.
  - **Spellcasting** (e.g. a one-third caster like the Eldritch Knight): caster type, ability, spell list, and the cantrips / prepared spells at each level (type them from your book). Spell slots are worked out (a one-third caster gets a full caster's slots at a third of its level, rounded up); level up asks for the cantrips and spells and sets the spellcasting ability.
- **Species:** size, speed, traits, and whether it gives a skill of choice.
- **Background:** the three abilities, two skills, tool, origin feat (add missing feats first), equipment and gold (the alternative is always 50 GP).
- **Feat:** origin / general / fighting style / epic boon, minimum level, an optional +1 ability increase, repeatable, description.
- **Class option:** an Eldritch Invocation (Warlock) or a Metamagic option (Sorcerer) — the SRD data has the features but not the lists. Minimum class level, a prerequisite shown with it, the Sorcery Points it costs, **Used as** (puts it in the sheet's Actions; a Metamagic option's Use spends its Sorcery Points) and **Switches on** (an attack modifier, e.g. Agonizing Blast), and **Spells it grants** — each cast with a slot, **at will**, or **free once per Long / Short Rest**, plus a note on what it adds (e.g. Mage Armor at will, on yourself only). Level up offers the options when the class gets new ones; granted spells go into the spellbook (always prepared) and get a **Cast free** button in Actions — once-per-rest ones are counted by a "<Spell> (free cast)" resource that comes back on that rest. A D&D Beyond sync marks the matching spells the same way.

**Formatting** works in every description: `**bold**`, `*italic*`, lines starting with `- ` as a list, and tables — lines of cells separated by `|` (a `|---|---|` line marks the header) or a table copied straight from a web page. The sheet's **Features** tab has a **📖 Read** view that shows it formatted (and **✏️ Edit** for the rows).

They appear in **New character** and **Level up** next to the SRD options, each card tagged with its source (SRD options say *SRD 5.2*). Only the one who added an entry, or the admin, can edit or delete it; deleting one doesn't change characters already built with it. Content is saved on your server only (`data/content.json`, included in backups) — the app itself never contains text from non-free books, so type it in yourself from your own copy.

## Familiars

A character's sheet has a **Familiar** panel (Actions tab). **Find a familiar…** lets you pick a form from the 2024 Find Familiar spell — Bat, Cat, Frog, Hawk, Lizard, Octopus, Owl, Rat, Raven, Spider, Weasel or any other CR 0 Beast — or one of the Pact of the Chain forms (Imp, Pseudodragon, Quasit, Skeleton, Sphinx of Wonder, Sprite, Venomous Snake), give it a name and make it a Celestial, Fey or Fiend. The sheet keeps its stat block and HP (with roll buttons for its actions). **Add to combat** (or "Add familiar" in the Combat Tracker) puts it in the fight with its own initiative; its player controls it, moves its token on the map, and its HP stays in step with the sheet.

## Campaigns

On the Characters page the DM opens **⚙ Manage campaigns**: create, rename or delete campaigns, pick one and tick the characters that belong to it — a character can be in several at once (a one-shot and the main campaign, say). **Retire** (DM, on the sheet) is for characters who died or left the party: they're kept, but hidden from the "Who are you?" screen, the Allies panels and the character list — tick **Show retired** to see them (and **Bring back** to undo).

**☆ Set as current** marks the campaign being played now: when someone opens the app and picks who they are, that campaign's characters come first (the others are folded under *Other campaigns*), new characters go into it, and in the Allies panel of the Combat Tracker and Battle Map the DM sees only its characters until they open *Characters in other campaigns*. Each campaign in that screen also has **+ New** to create a character directly in it.

## Adding to the fight (Combat Tracker and Battle Map)

Both pages have two panels you can open and close: **🛡 Allies** — the saved characters (by campaign) and their familiars, each with an initiative box (empty = d20 + DEX), plus a quick add for an NPC ally — and **⚔ Enemies** (DM only) — search the monster library, choose how many, optionally add them hidden for an ambush, or quick add a one-off enemy. Players see only **Join the battle** with their own character. On the map, new tokens appear under *Not on the map*; drag them onto the grid.

## Showing the map on a TV

`http://<server>:3000/tv` (or **📺 TV view** on the Battle Map page) is a full-screen, read-only map for a shared screen: the grid and background scaled to fit, a bar with the round, whose turn it is and the initiative order, a **Full screen** button, the cursor hidden when idle, and the screen kept awake. It always shows the **players' view** (no hidden monsters, aliases instead of real names, health words instead of monster HP) — even when the DM opens it.

**Apple TV** (it has no browser, so use AirPlay):
- **From a Mac (best):** Control Center → Screen Mirroring → your Apple TV → *Use As Separate Display*. On the Battle Map, click **📺 TV view**, drag the new window onto the TV display, click **Full screen**. You keep using your own screen as the DM.
- **From an iPad:** open `http://<server>:3000/tv` in Safari, turn the iPad to landscape, Control Center → Screen Mirroring → your Apple TV. (iPhone works too, with more black bars.)

With accounts, the TV's browser has to log in once (the DM's account is fine: the TV view always shows the players' view).

Other screens: an HDMI cable from a laptop (same as the Mac steps), Chromecast "Cast tab" from Chrome, or a TV/stick with a modern browser opening `/tv` directly.

## Accounts: admin, DMs and players

Everyone logs in with a username and password. There are three kinds of account:

- **Admin** — runs the server: manages every account and campaign, is DM of every table, makes backups. The first account is the admin.
- **DM** — can create new campaigns, and runs the ones they created.
- **Player** — plays their characters.

**Being DM is per campaign**, so one account can be DM in one campaign and a player in another. Whoever runs a campaign — its creator, or anyone the admin ticks under *Run by* in **Manage campaigns** (a player account too) — sees and controls only that campaign's characters, fight and battle map, and plays their own characters at the other tables. Switch between the two from the badge in the top bar.

**Running and playing at the same table:** the admin (or a DM) can also play a character in a campaign they run — click **+ New character** under that campaign on the "Who are you playing?" screen (a character made from a player view is yours; one made from the DM view is an NPC). The top bar then shows **🧝 Player view** / **👑 DM view** to switch in one click; the player view shows exactly what the players see.

**Each campaign is its own table**: its own fight (Combat Tracker) and battle map, so two groups can play at the same time without seeing each other's monsters. Characters in no campaign share the *No campaign* table (that's where everything happens if you don't use campaigns). The monster, item and spell libraries and the map backgrounds are shared by all DMs.

- **First start:** open the app — it asks to create the **admin account**. You need the **setup code** printed in the server log (`docker compose logs combat-tracker`, line "No DM account yet…"), which proves you run the server. Then you land on the **🔑 Players** page.
- **Inviting:** on *Players*, **Create invite link** — choose the role (the admin can invite players, DMs and admins), tick the campaigns they'll **play in**, the characters they'll play and (admin) the campaigns they'll **run** — and send the link. Example: DM of *Curse of Strahd* and a player in *Lost Mine* → role Player, *Plays in* Lost Mine, their character, *Runs* Curse of Strahd. It works once, for 7 days; they choose a username and password. A DM can invite players into their own campaigns.
- **A DM's first campaign:** after joining, a DM clicks **New campaign** on the "Who are you playing?" screen and is its DM at once. The admin can change who runs a campaign in **Manage campaigns** on the Characters page (*Run by*: any account, so a player can co-DM one campaign and keep playing in another).
- **Picking a table:** the badge in the top bar opens "Who are you playing?": one section per table you're at — **Run this table as the DM** (if you run it), your characters there, **+ New character** (it joins that table). The badge shows where you are ("👑 DM · Curse of Strahd").
- **Characters:** an account can play several characters; characters a player creates are theirs. On *Players* the admin (or the campaign's DM) adds accounts to campaigns and gives or takes away characters. Players can't move their characters to another campaign.
- **Forgotten password:** the admin makes a **Password reset link**. Everyone can **Change password** from the badge menu (other devices are logged out). The admin can also change roles, **Disable**, **Log out everywhere** or delete an account (its characters stay).
- **What players can't do or see:** they control only their own characters and see only the characters at their tables; they never receive DM-only information — monster HP/AC/stats (they see *Unhurt / Hurt / Bloodied / Near death / Down*), hidden combatants, real names behind an alias, DM notes, the monster library — or other people's accounts. The server checks every action against the logged-in account and table, not against what the browser claims.
- **No login at home:** set `KIT_AUTH=open` (see `docker-compose.yaml`) to go back to the old behaviour — one table, each browser just picks *I'm the DM* or a character. Only on a network you trust.

## Putting it on the internet

The app speaks plain HTTP; put something in front of it that adds **HTTPS** (passwords and the session cookie must not travel unencrypted). Any of these work:

- **A tunnel — no fixed IP, no open ports** (easiest while you don't have an address): [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) (`cloudflared tunnel --url http://localhost:3000`, or a named tunnel on your own domain) or [Tailscale Funnel](https://tailscale.com/kb/1223/funnel) (`tailscale funnel 3000`). HTTPS is handled by the tunnel.
- **A reverse proxy with your domain** (needs the domain pointing at the server and ports 80/443 open): e.g. [Caddy](https://caddyserver.com/), which gets a Let's Encrypt certificate by itself — a `Caddyfile` with `kit.example.com { reverse_proxy combat-tracker:3000 }` and a `caddy` service in `docker-compose.yaml`. nginx or Traefik work the same way (pass WebSocket upgrades through).

**With Tailscale Funnel** (on the machine that runs Docker): install Tailscale and `sudo tailscale up`; in the Tailscale admin console turn on MagicDNS and HTTPS certificates (DNS page) and allow Funnel for this machine (the first `tailscale funnel` run prints the link); then `sudo tailscale funnel --bg 3000`. `tailscale funnel status` shows the address (`https://<machine>.<tailnet>.ts.net`); `sudo tailscale funnel --https=443 off` stops it. Create invite links while you're on that address — they use the address in your browser.

Then, in `docker-compose.yaml`:

```yaml
    environment:
      TRUST_PROXY: "1"      # the proxy/tunnel is trusted for X-Forwarded-Proto/For
      COOKIE_SECURE: "1"    # the login cookie is only sent over HTTPS
    ports:
      - "127.0.0.1:3000:3000"   # if the proxy/tunnel runs on the same machine: no direct access from outside
```

**Updating a server** that runs the kit from a git clone: commit and push, then run `scripts/deploy.sh` on your computer. It connects over SSH, pulls `origin/master` on the server, saves the server's `data/` as a tarball in `~/deploy-snapshots` (newest 5 kept), rebuilds, waits for the health check and removes old images. `scripts/deploy.sh <commit>` deploys or rolls back to a specific commit. Settings go in a git-ignored `.env.deploy` in the repo root: `KIT_SERVER=ubuntu@<server-ip>` (required), `KIT_DIR` (the clone's folder in the server's home, default `DnD-combat-tracker`) and `KIT_URL` (checked at the end). Server-only files such as a `Caddyfile` and `docker-compose.override.yml` are left alone.

Built in: passwords hashed with scrypt, sessions in an `HttpOnly`, `SameSite=Lax` cookie (only a hash of each session token is stored), failed logins limited (10 per 15 minutes per username, 30 per address; successful logins don't count), invite and reset links used once and stored as hashes, requests and WebSocket connections from other sites refused, security headers (Content-Security-Policy, no framing, `nosniff`), WebSocket messages capped at 4 MB. Accounts and sessions live in `data/accounts.json`, `invites.json` and `sessions.json`; they are **not** included in *Download backup* (no password hashes in a downloaded file) and a restore never replaces them — copy them along with `data/` when moving the server.

## Data persistence

Each campaign's fight and map are saved in `combat.json` / `map.json` (one entry per campaign; files from before campaigns had their own table become the *No campaign* table). Character sheets are saved to `data/characters.json` (half a second after each change, and on shutdown) and loaded again on startup, so they survive restarts. With Docker, `docker-compose.yaml` mounts `./data` into the container, so they also survive rebuilds. Set `DATA_DIR` to store the file somewhere else. Back up that folder to back up your characters.

Campaigns, the monster, item and spell libraries and the list of battle map backgrounds are saved the same way (`data/campaigns.json`, `data/monsters.json`, `data/map-backgrounds.json`); background images themselves are files in `data/maps/`.

The current fight (combatants, HP, round, turn) and the battle map (grid size, token positions, background) are saved too, so a restart or a rebuild doesn't lose them. **Clear** on the Combat Tracker starts a new fight.

**Backups:** as the DM, use **Backup & restore** at the bottom of the Home page. *Download backup* saves everything above (map images included) as one `.json` file; *Restore from file…* puts such a file back for everyone at the table, live — the data it replaces is first saved in `data/backups/` (the last 5 restores are kept).

**Automatic backups:** the server also writes the same backup file to `data/backups/` **every week** by itself and keeps the **newest two** (a server that was switched off catches up shortly after it starts). The admin sees them under *Backup & restore* on the Home page, with a download button; to go back to one, download it and use *Restore from file…*. They sit in the same `data/` folder as everything else, so copy one somewhere else now and then (another disk, cloud storage) in case the disk itself fails. Change the schedule with `AUTO_BACKUP_DAYS` (0 = off) and `AUTO_BACKUP_KEEP` in `docker-compose.yaml`.

## How it works

The server is the single source of truth. A client sends an action `{ type, payload }`; the server applies it and broadcasts the updated slice of state to **all** clients, including the sender. Clients only render what the server last sent them.

There are two state slices, both sent to every client on connect:

| Feature | Broadcast message |
|---|---|
| combat | `{ type: 'state', state }` |
| characters | `{ type: 'charState', characters }` |

## Adding things

**A new tool** (e.g. a dice roller with shared history)
1. Server: create `src/features/<name>/` with `service.js`, `actions.js` and an `index.js` exporting `{ name, wire: { type, key }, snapshot, actions }`, then add it to the `createHub` list in `src/app.js`. The hub handles routing, broadcasting and sending the slice on connect. If an action also changes another feature, list it in `alsoBroadcast`.
2. Client: add `public/<name>.html`, `public/js/<name>/main.js`, `public/css/pages/<name>.css`, and one entry in `public/js/core/tools.js` (the nav bar and the home cards are generated from it).

**A new importer**: add a folder under `src/features/imports/` with a router factory, and register it in `src/features/imports/index.js`. Keep the mapper (pure function) separate from the code that touches the network or files so it stays easy to test.

**A new character field**: add it to `blankCharacter` and `sanitizeCharacterPatch` in `src/features/characters/model.js`, then bind it in `public/js/characters/editor/` (`FIELD_MAP` in `fields.js` for simple inputs).

## Notes on the D&D Beyond importer

It uses D&D Beyond's unofficial character endpoint, so the character's sharing must be set to **Public**. AC and proficiencies are a best-effort estimate. Non-OK and unusable responses are logged on the server (`docker compose logs`) with the status and the start of the response body.
