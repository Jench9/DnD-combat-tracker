# Adventurer's Kit

A self-hosted D&D 5e toolkit for the table: a **Combat Tracker**, **Character Sheets** (with D&D Beyond and PDF import), a **Monsters** library, an **Items** library (SRD weapons/armor/gear + custom items), a **Spells** library (common SRD spells + custom ones; characters get spell slots and cast from their Actions) and a grid **Battle Map**, synced live across every device connected to the server. One player bumps a monster's HP and everyone's screen updates instantly.

A small Node server holds the state (saved to JSON files on disk, including the current fight) and pushes updates to every browser over WebSocket. No accounts, no database, no build step.

## Run it

### With Docker (recommended)

```bash
docker compose up -d --build
```

Open **http://localhost:3000**. Stop with `docker compose down`, follow logs with `docker compose logs -f combat-tracker`.

The image bakes the code in, so **any change needs a rebuild** (`docker compose up -d --build`). For live reload while developing:

```bash
docker compose -f docker-compose.dev.yml up --build
```

### Without Docker

```bash
npm ci
npm start
```

Requires Node 20.9+ (for `sharp`, which resizes imported avatars; on older Node the app still runs but D&D Beyond avatars are skipped).

### Tests

```bash
npm test
```

Runs the server tests (`node:test`, no extra dependencies): WebSocket flows for both features, input sanitising, and the importers' mapping logic.

## Letting friends connect

- **Same wifi**: they open `http://<your-LAN-IP>:3000`. Find your IP with `ipconfig getifaddr en0` (Mac) or `ipconfig` (Windows).
- **Different networks**: use a tunnel (`ngrok`, `cloudflared`) or deploy to a VPS / container platform behind a reverse proxy with HTTPS.

## SRD content

The item, spell and monster libraries come with the full **System Reference Document 5.1 (2014 rules) and 5.2 (2024 rules)**: every SRD spell, weapon, armor, piece of gear, magic item and creature. The table plays **2024 rules**: where both editions have the same entry, the 2024 one has the plain name and the 2014 one is "… (2014)" (libraries saved with the older naming are renamed automatically, keeping each entry's id). This is the openly licensed (CC-BY-4.0) part of D&D — content that's only in the paid books (the rest of the Player's Handbook, Xanathar's, …) isn't included; add it as custom entries. See [NOTICE.md](NOTICE.md).

The data lives in `src/srd/*.json`, generated by `scripts/build-srd.js` from the open [5e-bits/5e-database](https://github.com/5e-bits/5e-database). To regenerate it, download `src/2014/en/5e-SRD-{Spells,Equipment,Magic-Items,Monsters}.json` and the same four from `src/2024/en/` into a folder as `2014-Spells.json`, …, `2024-Monsters.json`, then run `npm run build:srd -- <folder>`. On the next start, each library merges the new data in once (SRD entries are updated in place, custom ones are left alone).

## Creating characters and leveling up

**+ New character** on the Character Sheets page (and *Create a new character* on the "Who are you?" screen) opens a step-by-step creator for the **2024 rules**: class → species → background → ability scores (standard array, point buy, 4d6 drop lowest — your own dice when the top bar says ✋ Hand dice — or your own numbers) → skills (plus Fighting Style / Expertise where the class gets them) → spells → starting equipment → name. It fills in the whole sheet: HP, saves, skills, feats, attack modifiers, spell slots, class resources, gear and gold, and the rules text of every trait and feature in Features. **Blank sheet** still gives an empty sheet to fill in by hand.

**⬆ Level up** on a sheet adds one level: pick the class (or multiclass into a new one, if you have the 13s), take the average or roll for hit points, and answer what that level asks for — subclass, Ability Score Improvement or a feat, Epic Boon, Fighting Style, Expertise, new cantrips and spells. Hit Dice, spell slots (multiclass table and Pact Magic included), class resources (Rage, Channel Divinity, Focus Points…) and the new feature texts are updated for you. It also works on characters imported from D&D Beyond or typed in by hand (it reads the class from the sheet, e.g. "Fighter 3 / Wizard 2"); classes that aren't in the SRD are kept but leveled by hand.

The rules come from the SRD 5.2, so each class has one subclass, and there are four backgrounds and only the SRD feats. For anything from the books, choose "Other" (subclass, feat) and add its text to the sheet. Eldritch Invocations, Metamagic, Weapon Mastery choices and languages are listed as "by hand" reminders. The data is `src/srd/rules-2024.json`, generated by `scripts/build-rules.js`: download `src/2024/en/5e-SRD-{Classes,Levels,Features,Subclasses,Species,Subspecies,Traits,Backgrounds,Feats}.json` from 5e-database into a folder as `2024-Classes.json`, … and run `npm run build:rules -- <folder>`.

## Familiars

A character's sheet has a **Familiar** panel (Actions tab). **Find a familiar…** lets you pick a form from the 2024 Find Familiar spell — Bat, Cat, Frog, Hawk, Lizard, Octopus, Owl, Rat, Raven, Spider, Weasel or any other CR 0 Beast — or one of the Pact of the Chain forms (Imp, Pseudodragon, Quasit, Skeleton, Sphinx of Wonder, Sprite, Venomous Snake), give it a name and make it a Celestial, Fey or Fiend. The sheet keeps its stat block and HP (with roll buttons for its actions). **Add to combat** (or "Add familiar" in the Combat Tracker) puts it in the fight with its own initiative; its player controls it, moves its token on the map, and its HP stays in step with the sheet.

## Joining from the Battle Map

The Battle Map has a **Join the battle** panel (DM: **Add characters to the battle**), the same list as on the Combat Tracker: type your initiative roll (or 🎲, or leave it empty for d20 + DEX) and **Add**. Your token appears under *Not on the map*; drag it onto the grid. Players see only their own character and familiar; the DM sees everyone, by campaign.

## Showing the map on a TV

`http://<server>:3000/tv` (or **📺 TV view** on the Battle Map page) is a full-screen, read-only map for a shared screen: the grid and background scaled to fit, a bar with the round, whose turn it is and the initiative order, a **Full screen** button, the cursor hidden when idle, and the screen kept awake. It always shows the **players' view** (no hidden monsters, aliases instead of real names, health words instead of monster HP) — even when the DM opens it.

**Apple TV** (it has no browser, so use AirPlay):
- **From a Mac (best):** Control Center → Screen Mirroring → your Apple TV → *Use As Separate Display*. On the Battle Map, click **📺 TV view**, drag the new window onto the TV display, click **Full screen**. You keep using your own screen as the DM.
- **From an iPad:** open `http://<server>:3000/tv` in Safari, turn the iPad to landscape, Control Center → Screen Mirroring → your Apple TV. (iPhone works too, with more black bars.)

Other screens: an HDMI cable from a laptop (same as the Mac steps), Chromecast "Cast tab" from Chrome, or a TV/stick with a modern browser opening `/tv` directly.

## DM and players

There are no accounts. The first time someone opens the app they pick **I'm the DM**, their character, or **Create a new character**; the badge in the top bar switches later. The DM sees and controls everything. Players control only their own character (sheet, HP and conditions in combat, map token, ending their own turn) and never receive DM-only information: monster HP/AC/stats (they see *Unhurt / Hurt / Bloodied / Near death / Down*), combatants the DM has hidden, real names behind an alias, DM notes, or the monster library. It's not a login: anyone can choose to be the DM — it just keeps secrets off the players' screens.

## Data persistence

Character sheets are saved to `data/characters.json` (half a second after each change, and on shutdown) and loaded again on startup, so they survive restarts. With Docker, `docker-compose.yaml` mounts `./data` into the container, so they also survive rebuilds. Set `DATA_DIR` to store the file somewhere else. Back up that folder to back up your characters.

Campaigns, the monster, item and spell libraries and the list of battle map backgrounds are saved the same way (`data/campaigns.json`, `data/monsters.json`, `data/map-backgrounds.json`); background images themselves are files in `data/maps/`.

The current fight (combatants, HP, round, turn) and the battle map (grid size, token positions, background) are saved too, so a restart or a rebuild doesn't lose them. **Clear** on the Combat Tracker starts a new fight.

**Backups:** as the DM, use **Backup & restore** at the bottom of the Home page. *Download backup* saves everything above (map images included) as one `.json` file; *Restore from file…* puts such a file back for everyone at the table, live — the data it replaces is first saved in `data/backups/` (the last 5 restores are kept).

## How it works

The server is the single source of truth. A client sends an action `{ type, payload }`; the server applies it and broadcasts the updated slice of state to **all** clients, including the sender. Clients only render what the server last sent them.

There are two state slices, both sent to every client on connect:

| Feature | Broadcast message |
|---|---|
| combat | `{ type: 'state', state }` |
| characters | `{ type: 'charState', characters }` |

## Adding things

**A new tool** (e.g. a dice roller with shared history)
1. Server: create `src/features/<name>/` with `service.js`, `actions.js` and an `index.js` exporting `{ name, wire: { type, key }, snapshot, actions }`, then add it to the `createHub` list in `src/app.js`. The hub handles routing, broadcasting and sending the slice on connect. If an action also changes another feature, list it in `alsoBroadcast`.
2. Client: add `public/<name>.html`, `public/js/<name>/main.js`, `public/css/pages/<name>.css`, and one entry in `public/js/core/tools.js` (the nav bar and the home cards are generated from it).

**A new importer**: add a folder under `src/features/imports/` with a router factory, and register it in `src/features/imports/index.js`. Keep the mapper (pure function) separate from the code that touches the network or files so it stays easy to test.

**A new character field**: add it to `blankCharacter` and `sanitizeCharacterPatch` in `src/features/characters/model.js`, then bind it in `public/js/characters/editor/` (`FIELD_MAP` in `fields.js` for simple inputs).

## Notes on the D&D Beyond importer

It uses D&D Beyond's unofficial character endpoint, so the character's sharing must be set to **Public**. AC and proficiencies are a best-effort estimate. Non-OK and unusable responses are logged on the server (`docker compose logs`) with the status and the start of the response body.
